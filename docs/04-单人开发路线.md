# 04 · 单人开发路线

> 平台愿景与范式见 [00-AI原生数据平台范式](00-AI原生数据平台范式.md)。
> 本文只回答一件事：**一个人怎么在 16 周内走到 L2（数字可信的问数），再逐步够到 L3。**
>
> 结论先行：**一个人从零做「平台」，按平台做必死；按「一条竖切」做才有活路。**
>
> 全职约 **14~16 周**到内部可用 v1；业余（每天 2~3 小时 + 周末）约 **6~8 个月**。
> 时间估算的前提是「严格按本文的砍掉清单执行」，不包含采集/清洗的不可控部分。

---

## 一、三条铁律

1. **每个阶段结束都必须有能给人看的产出**，否则极易烂尾。
2. **不做的清单要长于做的清单**。单人的最大风险不是技术，是范围。
3. **数据比代码重要**。没有数据，平台做完也是空壳。第 1 周就要碰真实数据。

---

## 二、阶段总览（全职）

| 阶段 | 周期 | 目标 | 验收 |
|---|---|---|---|
| **v0.1 能问数** | 4 周 | 数据落地 + 语义层 + 问数 + 单页界面 | 10 个真实问题，规则引擎答对 ≥ 6 个 |
| **v0.2 能沉淀** | 3 周 | Pin + 看板 + 分享链接 | 业务同学自己问、自己存、自己分享 |
| **v0.3 能维护** | 4 周 | Excel 导入、业务库接入、语义层配置化 | 不用改代码就能加指标 |
| **v1.0 能推广** | 4 周 | 登录、权限、目录、缓存与性能 | 10+ 人日常使用 |

> 本文写于骨架已跑通之后，v0.1 的实际代码见仓库，按它往下推即可。

---

## 三、v0.1 详细计划（4 周）

| 周 | 任务 | 具体产出 | 风险点 |
|---|---|---|---|
| W1 | 数据落地 | 定 3~5 张标准表；`import_excel.py`；把真实 Excel 灌进仓库表 | **真实数据可能拿不到**，先用合成数据跑机制 |
| W2 | 语义层 + 编译器 | 真实业务域的 YAML；`check_semantic.py` 全绿；手写 QuerySpec 能查对 | 指标口径和业务对不齐 |
| W3 | 问数 | 同义词、值字典、时间解析；规则引擎 + 评测集 | 规则引擎覆盖度不够 |
| W4 | 界面 + 评测 | 单页问数界面；20 条评测集；埋点 | 前端时间失控 |

**W4 结束的决策点**：

| 现象 | 结论 |
|---|---|
| 10 个真实问题答对 ≥ 6 个 | 继续 v0.2 |
| 答对 3~5 个 | 先补语义层和值字典，不要接 LLM |
| 答对 < 3 个 | 说明业务域还没摸清，停下来和业务对齐 |

> 这份骨架里的规则引擎就是「基线」。LLM 至少要打得过它，否则没有价值。

## 四、v0.2 能沉淀（3 周）

| 周 | 任务 |
|---|---|
| W5 | 看板数据模型 + 布局渲染 + 卡片刷新 |
| W6 | Pin 交互、看板列表、草稿/发布状态 |

验收：**一个业务同学独立完成「问 → 存 → 发给同事看」全流程**。

---

## 五、v0.3 能维护（4 周）

一个人维护平台的最大成本是「加一个指标要改代码」。这阶段目的是把它变成配置。

| 周 | 任务 |
|---|---|
| W8 | ~~Excel/CSV 导入（拖文件 → 落表 → 自动推断字段）~~ ✅ **已实现**：`datasets.py` + 「数据」页 |
| W9 | 业务库接入（MySQL/PG 只读账号 + 定时同步到本地仓库） |
| W10 | ~~语义层配置页面（指标 CRUD、同义词、值字典）~~ ✅ **已实现对话式版本**：`builder.py` + 「开发」页（自然语言加指标/改名/加同义词/回退/校验） |
| W11 | 语义模型版本化与校验（提交前跑 CLI） |

> 这阶段可以不做 UI，先用 YAML + CLI。**配置页面的投入产出比远低于数据接入**。

## 七、砍掉清单（明确不做）

| 不做 | 原因 | 什么时候再说 |
|---|---|---|
| 多租户 SaaS | 内部工具，无需求 | 永不 |
| SSO / 企业微信登录 | 加分项不是必需 | v1.0 后 |
| 拖拽式看板编辑器 | 投入 3~4 周，产出有限 | v1.0 后 |
| 地图 / 大屏 / 移动端 | 演示价值 > 使用价值 | 有明确需求再说 |
| 订阅推送 / 嵌入 iframe | 分享链接够用 | v1.0 后 |
| 多数据源联邦查询 | 先统一落地到本地仓库 | 数据量撑不住再说 |
| 微服务 / K8s / 完整 CI/CD | 一个人维护不动 | 有团队再说 |
| 自研图表库 | 用现成的 | 永不 |

---

## 八、单人特有的风险

| 风险 | 表现 | 对策 |
|---|---|---|
| **数据拿不到** | 卡在"等业务给数据" | 先用合成数据跑机制；同时推进数据获取 |
| **范围膨胀** | 做着做着想做"完整平台" | 每两周对照砍掉清单复盘一次 |
| **前端失控** | 想做大屏、想上 React 全家桶 | v1.0 前只用单页 + 手写 SVG/ECharts |
| **只有你懂** | 请假一周没人能接手 | 语义模型走 Git、写评测集、README 保持可运行 |
| **口径漂移** | 业务说"这个数不对" | 每次回答都展示口径和 SQL；关键指标人工对账期 |
| **测试缺失** | 改一处崩三处 | 至少保住编译器测试 + 评测集 |

---

## 九、什么信号说明该加人

- 语义层维护占你 > 30% 时间 → 加数据工程
- 需求排队 > 2 个月 → 加前端
- 准确率卡在 60% 上不去 → 加算法/AI
- 日活 > 50 且查询变慢 → 加后端

---

## 十、如果只能给一个建议

**先把「一个业务问题的完整闭环」跑通，再谈平台。**

问一句话 → 查出对的数 → 看到图 → 存成看板 → 发链接给同事。
这五步跑通，后面所有工作都是在这个骨架上加肉；跑不通，做再多模块也是零。

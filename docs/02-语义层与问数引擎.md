# 02 · 语义层与问数引擎

本文件定义两个核心契约：**语义模型（YAML）** 和 **QuerySpec（JSON）**。
它们是整个系统的接口，前后端、AI、编译器都围绕它们工作。

---

## 一、语义模型规范

### 1.1 文件结构

一个语义模型 = 一个业务域（如「电商交易域」），一个 YAML 文件。

```yaml
version: 1
name: ecommerce
title: 电商交易域
description: 订单、商品、用户相关的核心指标

datasource: main_mysql        # 引用数据源连接
fact_table: fact_order        # 默认事实表
fact_alias: f

joins: [...]                  # 维表关联
dimensions: [...]             # 维度
metrics: [...]                # 指标
synonyms: {...}               # 全局同义词
rls: [...]                    # 行级权限
```

### 1.2 指标（metrics）

指标分三类，编译方式不同。

#### (a) 原子指标 atomic

```yaml
- name: gmv
  title: GMV
  type: atomic
  agg: sum                    # sum | count | count_distinct | avg | min | max
  column: f.paid_amount
  filters:                    # 恒定的过滤条件，编译时 AND 进 WHERE
    - "f.status = 'paid'"
  format: currency            # currency | percent | integer | number | duration
  synonyms: [GMV, 成交额, 销售额, 营收, 交易额]
```

**关键约束**：`filters` 是指标口径的一部分。「GMV」定义为已支付，这个条件写在这里，不在问数时由 LLM 猜。

#### (b) 派生指标 derived

由其他指标计算，只能引用**同一语义模型内**的指标：

```yaml
- name: aov
  title: 客单价
  type: derived
  expr: "{gmv} / {order_cnt}"   # 编译器自动加 NULLIF 防除零
  format: currency
  synonyms: [客单价, 客单, 平均订单金额]

- name: refund_rate
  title: 退款率
  type: derived
  expr: "{refund_gmv} / {gmv}"
  format: percent
```

#### (c) 窗口指标 window

与时间窗口相关，必须在查询带时间维度时才能算：

```yaml
- name: gmv_mom
  title: GMV 环比
  type: window
  base: gmv
  window: mom                 # mom | yoy | wow | cumulative
  format: percent
```

#### 指标表达式语法（`expr` 字段）

```
expr      := operand (("+"|"-"|"*"|"/") operand)*
operand   := "{" metric_name "}" | number | "(" expr ")"
```

只允许四则运算和指标引用，**不允许写 SQL 函数**——需要的话就加新指标。

### 1.3 维度（dimensions）

```yaml
- name: order_date
  title: 下单日期
  type: time
  column: f.paid_at
  granularities: [day, week, month, quarter, year]
  synonyms: [日期, 时间, 下单时间, 支付时间]

- name: channel
  title: 渠道
  type: string
  column: f.channel
  synonyms: [渠道, 来源, 流量来源]
  dictionary: [直播, 搜索, 推荐, 自然流量, 广告]   # 用于实体链接和澄清

- name: region
  title: 地区
  type: string
  column: u.province
  synonyms: [地区, 区域, 省份]
```

`dictionary` 的作用：问「华东的 GMV」，实体链接阶段要把「华东」精确匹配到 `region` 维度。没有字典就只能靠 LLM 猜，准确率暴跌。字典可以手工维护，也可以从库里 `SELECT DISTINCT` 采样后人工确认。

### 1.4 关联（joins）

```yaml
joins:
  - table: dim_user
    alias: u
    type: left
    on: "f.user_id = u.user_id"
  - table: dim_product
    alias: p
    type: left
    on: "f.product_id = p.product_id"
```

**防扇出规则**：编译器只 join 查询实际用到的表；如果某个指标的 `fact_table` 与主事实表不同，走「指标分组」编译（见 1.7）。

### 1.5 同义词（synonyms）

```yaml
synonyms:
  "上月": "last_month"
  "环比": "mom"
  "同比": "yoy"
  "TOP10": "top 10"
```

用于问题归一化，把口语映射成规范时间词 / 操作词。

### 1.6 权限（rls / cls）

```yaml
rls:
  - dimension: region
    apply_to: [u.province]
    rule: "u.province IN ({{ user.regions }})"
    when: "user.regions is not empty"     # 可选条件

cls:
  - column: u.phone
    roles: [analyst, admin]
```

编译期注入，LLM 不可见。

### 1.7 指标分组编译（解决多事实表混算）

不同指标来自不同事实表时，直接 join 会重复计数。编译器按 `fact_table` 分组：

```
指标组 A（fact_order）: gmv, order_cnt
指标组 B（fact_refund）: refund_gmv

→ 先各自按维度聚合出子查询
→ 再按维度 FULL OUTER JOIN 对齐
→ 最后外层计算派生指标 refund_rate
```

### 1.8 语义模型校验规则

加载时强校验，任何一条不通过直接拒绝启动：

| 规则 | 说明 |
|---|---|
| 命名唯一 | metric / dimension 在模型内唯一 |
| 引用有效 | derived 表达式引用的指标必须存在 |
| 无循环 | derived 指标依赖图不能有环 |
| 无歧义 | 维度列在多张 join 表出现时必须带表别名 |
| 口径完整 | atomic 指标必须有 `agg` 和 `column` |
| 时间维度 | 至少有 1 个 time 维度，否则趋势类问题无法回答 |
| 权限可解析 | `rule` 里的 `{{ user.xxx }}` 变量必须在权限上下文里有定义 |

### 1.9 知识层：语义层之外的另一半

语义层回答「**怎么算**」，知识层回答「**为什么这么算、口径什么含义、怎么解读**」。两者分开存，因为变更频率完全不同：

| | 语义层 `ecommerce.yaml` | 知识层 `knowledge.yaml` |
|---|---|---|
| 内容 | 指标表达式、维度、关联、RLS | 业务含义、负责人、变更记录、解读提示、FAQ |
| 改的人 | 数据工程 | 业务方 / 分析师 |
| 改的频率 | 低（口径变更） | 高（答疑、补充说明） |
| 作用 | 编译 SQL | 支撑「AI 解释数据」 |

```yaml
metrics:
  gmv:
    business_meaning: 已支付订单的商品成交金额，不含运费、不含税、不含退款
    owner: 交易数据组
    updated_at: "2026-03-12"
    interpretation:
      - 月末和月中（15~17 号）通常有促销，出现峰值属正常
    faq:
      - q: 为什么和财务口径对不上？
        a: 财务口径含运费与税，且按开票确认收入
    history:
      - date: "2026-03-12"
        change: 口径从含运费改为不含运费，历史数据已重刷
```

平台自动从语义层计算**血缘**（指标 → 字段 → 表）和**影响面**（哪些指标依赖它），从知识层取**业务解释**。两者拼起来，才能回答「这个数怎么来的」而不靠模型编。

> 已实现：`server/app/knowledge.py`，接口 `GET /api/queries/{id}/explain`。

## 二、QuerySpec 规范

QuerySpec 是「一次问数的确定性描述」，LLM 的输出、编译器的输入、看板的持久化对象，都是它。

```json
{
  "version": 1,
  "metrics": ["gmv"],
  "dimensions": ["order_date"],
  "filters": [
    { "type": "dimension", "dimension": "channel", "op": "in", "values": ["直播"] },
    { "type": "time", "dimension": "order_date",
      "range": { "type": "absolute", "start": "2026-09-01", "end": "2026-09-30" },
      "grain": "day" }
  ],
  "compare": { "mode": "previous_period" },
  "order_by": [{ "by": "gmv", "dir": "desc" }],
  "limit": 100,
  "viz_hint": "line"
}
```

### 字段说明

| 字段 | 必填 | 说明 |
|---|---|---|
| `metrics` | 是 | 指标名列表，至少 1 个 |
| `dimensions` | 否 | 分组维度；为空表示整体汇总 |
| `filters` | 否 | `type=dimension` 普通过滤；`type=time` 时间范围 |
| `compare` | 否 | `previous_period` / `same_period_last_year` / `none` |
| `order_by` | 否 | 排序，默认按第一个指标降序 |
| `limit` | 否 | 默认 500，硬上限 5000 |
| `viz_hint` | 否 | LLM 可给建议，但最终图表由表达层推断 |

### 时间表达（`range`）

```json
{"type": "relative", "value": "last_month"}
```

支持的相对值：`today` `yesterday` `last_7d` `last_30d` `this_week` `this_month` `last_month` `this_quarter` `last_quarter` `this_year` `last_year`。
**相对时间在编译时才解析成绝对日期**，这样看板订阅每天刷新时数字会变——这是沉淀能力的前提。

## 三、SQL 编译算法

```python
def compile(spec, model, user):
    # 1. 选中表：主事实表 + 维度/过滤涉及的维表
    tables = resolve_tables(spec, model)

    # 2. 按 fact_table 分组
    groups = group_metrics_by_fact(spec.metrics, model)

    # 3. 每组生成聚合子查询（维度 + 过滤 + 指标自身的 filters）
    subs = [build_agg_subquery(g, spec, model) for g in groups]

    # 4. 多组时按维度 join；单组直接产出
    sql = assemble(subs, spec.dimensions)

    # 5. 注入行级权限（改 WHERE，不改结果）
    sql = inject_rls(sql, model, user)

    # 6. 外层计算派生指标 / 窗口指标
    sql = apply_derived(sql, spec.metrics, model)

    # 7. 排序 + limit + 时间桶表达式
    return sql
```

### 编译示例

输入：

```json
{"metrics": ["gmv","order_cnt"], "dimensions": ["order_date"],
 "filters": [{"type":"dimension","dimension":"channel","op":"in","values":["直播"]},
             {"type":"time","dimension":"order_date","range":{"type":"relative","value":"last_month"},"grain":"day"}]}
```

输出：

```sql
SELECT
  DATE_FORMAT(f.paid_at, '%Y-%m-%d') AS order_date,
  SUM(f.paid_amount)                 AS gmv,
  COUNT(DISTINCT f.order_id)         AS order_cnt
FROM fact_order f
LEFT JOIN dim_user u ON f.user_id = u.user_id
WHERE f.status = 'paid'
  AND f.channel IN ('直播')
  AND f.paid_at >= '2026-09-01' AND f.paid_at < '2026-10-01'
  AND u.province IN ('华东','华南')          -- RLS 注入
GROUP BY 1
ORDER BY 1
LIMIT 500
```

### 安全边界

编译层只接受语义模型里声明过的指标/维度，天然阻断：

- 直接写表名的注入
- `DROP` / `UPDATE` / 多语句
- 未授权字段访问
- 全表扫描（强制带时间范围或 LIMIT）

## 四、问数流水线

```
question
  → ① 归一化 normalize       同义词替换、指代消解、单位统一
  → ② 意图分类 intent          aggregate | detail | trend | compare | ranking | share | ratio
  → ③ 实体链接 link           指标 / 维度 / 维度值 / 时间 / 过滤 / 排序 / limit
  → ④ 槽位校验 validate       缺什么？有默认值吗？需要澄清吗？
  → ⑤ 规划 plan              生成 QuerySpec（LLM 在候选集内选择 + 规则兜底）
  → ⑥ 编译 compile           SQL + RLS
  → ⑦ 预检 precheck          EXPLAIN、估算行数、耗时
  → ⑧ 执行 execute           带缓存
  → ⑨ 校验 verify            空结果 / 行数异常 / 量级突变
  → ⑩ 表达 render            图表 + 文字结论 + 口径/SQL 可展开
```

### 各阶段失败策略

| 阶段 | 失败表现 | 处理 |
|---|---|---|
| 实体链接 | 指标找不到 | 返回候选让用户选（「你是说 GMV 还是 成交订单数？」） |
| 槽位校验 | 缺时间 | 默认 `last_30d` 并在回答里明示 |
| 预检 | 估算耗时 > 30s | 拒绝并建议加时间范围 / 降低粒度 |
| 执行 | SQL 报错 | 把错误回喂 LLM 重试（≤2 次） |
| 结果校验 | 空结果 | 提示可能的过滤原因，不直接说"没有数据" |
| 结果校验 | 量级异常（同比 >5 倍） | 正常返回但标黄提示，避免误导 |

### 延迟预算（P50 目标 6s）

| 环节 | 预算 |
|---|---|
| 意图 + 链接（小模型） | 0.8s |
| 规划（大模型） | 2.5s |
| 编译 | <50ms |
| 执行 | 1.5s（缓存命中 <100ms） |
| 表达 | <100ms |

超过预算就流式返回中间状态（「正在识别指标…」「正在查询…」）。

## 五、多轮对话

**不要每轮都把历史对话丢给 LLM 重新生成。** 维护会话状态：

```json
{
  "session_id": "s_xxx",
  "last_spec": { ... },
  "last_result": { "rows": 31, "columns": ["order_date","gmv"], "value_range": [0, 1e6] },
  "entities": { "gmv": "gmv", "直播": "channel=直播", "9月": "2026-09" },
  "pending_clarification": null
}
```

### 三种轮次类型

| 类型 | 例子 | 处理 |
|---|---|---|
| 新问题 | 「看下退款率」 | 全新规划 |
| 修正式 | 「按地区拆一下」「换成环比」 | 对 `last_spec` 做 **patch** |
| 追问式 | 「为什么 9 月 3 号掉了」 | 沿用 spec + 下钻，可能触发新查询 |

### Patch 格式

```json
[
  {"op": "replace", "path": "/dimensions", "value": ["region"]},
  {"op": "replace", "path": "/compare", "value": {"mode": "previous_period"}}
]
```

可 patch 的字段白名单：`dimensions` `filters` `compare` `order_by` `limit` `time.grain`。
不可 patch：`metrics` 的增删要重新走实体链接（避免语义漂移）。

## 六、可解释性（必做）

每个回答必须能展开三样东西：

1. **口径**：涉及哪些指标，定义是什么，有哪些过滤条件
2. **SQL**：实际执行的语句（可复制）
3. **口径来源**：`语义模型 ecommerce.yaml / metric: gmv / v3`

没有这三样，业务不会在对账场景信任系统。

## 七、评测体系

### 7.1 数据集格式

```yaml
- id: q001
  question: 上个月 GMV 是多少
  category: single_metric
  difficulty: easy
  expected_spec:
    metrics: [gmv]
    filters: [{type: time, range: {type: relative, value: last_month}}]
  expected_answer:
    gmv: 1234567.89
  tolerance: 0.01
```

### 7.2 分层指标

| 指标 | 含义 | P0 目标 |
|---|---|---|
| 意图准确率 | 分类正确 | ≥ 90% |
| 实体链接准确率 | 指标/维度/值选对 | ≥ 85% |
| QuerySpec 完全匹配率 | 结构化字段全对 | ≥ 70% |
| SQL 执行成功率 | 不报错 | ≥ 95% |
| 答案正确率 | 数值在容差内 | ≥ 70% |
| 澄清率 | 需要反问的比例 | ≤ 20% |
| P50 延迟 | 端到端 | ≤ 6s |

### 7.3 用法

- 每次改 prompt / 换模型 / 改语义层 → CI 跑全量
- 线上抽样：用户点「👎」的记录自动进「待标注」队列，标注后进评测集
- 评测集按 category 分组看，不要只看总分——`ranking` 类问题通常最差

### 7.4 分类覆盖（建集时保证）

`single_metric` `multi_metric` `trend` `compare` `ranking` `share` `ratio` `filter` `time_range` `ambiguous` `unanswerable`

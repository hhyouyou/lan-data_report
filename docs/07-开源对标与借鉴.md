## 二、四个梯队，各有什么用

### 第一梯队：语义层 + 问数（最值得读）

**SuperSonic（腾讯音乐）** —— 架构上最接近我们的设计：

- 明确提出 **Chat BI（LLM）+ Headless BI（语义层）双范式**
- 核心是「指标 + 维度 + 术语」三件套的语义建模
- 解析分两阶段：LLM 做**术语映射与 schema 链接** → 确定性组件做**语义解析**生成指标查询
- 这正好印证我们「LLM 只做规划，SQL 由编译器生成」的选择

**Wren AI** —— 产品链路最接近：

- 用「context layer」把自然语言转成受控 SQL
- 有完整的 question → SQL → chart → 保存 的闭环
- 它的 **MDL（Modeling Definition Language）** 和我们的 `semantic/*.yaml` 是同一类东西，值得逐字段对照

### 第二梯队：AI 数据 Agent

**DB-GPT** —— 值得学 Agent 编排与 AWEL（工作流 DSL），但它是「框架」定位，不是「内部平台」。它的 6 个 Agent 场景和我们「数据开发 / 分析 / 消费」三类角色有对应关系。

### 第三梯队：治理与上下文层

**DataHub / OpenMetadata** —— 这两家 2026 年都把定位改成了 **Context Platform / Open Context Layer**。它们的价值在：

- 血缘模型（upstream / downstream、字段级）
- 术语表（Glossary）、分类（Classification）、数据契约
- 变更影响分析

这正是我们「知识资产 + 解释数据」的上游。**但它们的体量（590 MB / 3 GB）对一个人来说是灾难。**

### 第四梯队：建模与 BI 工具

**dbt** —— 不是平台，是「建模即代码」的工程范式：Git MR、测试、exposures（指标被哪些看板用了）。我们的 `semantic_gate.py` + Git MR 就是这套思路的迷你版。

**Chat2DB** —— 定位是数据库客户端，不是平台。可以借鉴它的「AI 解释 SQL / 优化 SQL」交互。

**Vanna（已归档）** —— 曾经的 text-to-SQL 明星，2026-02 后停更。**不建议作为依赖。**

## 三、抄什么，不抄什么

| 来源 | 抄 | 不抄 |

| dbt | Git MR + 测试 + exposures 的工程习惯 | 调度执行 |

## 四、为什么说「没有完全对标」

拆成四类资产看：

| 能力 | Wren | SuperSonic | Cube | DataHub | OpenMetadata | **我们** |
|---|---|---|---|---|---|---|
| 语义层 | ✅ | ✅ | ✅ | 部分 | 部分 | ✅ |
| 自然语言问数 | ✅ | ✅ | 部分 | ❌ | ❌ | ✅ |
| 看板沉淀 | ✅ | ✅ | ❌ | ❌ | ❌ | ✅ |
| 知识/口径解释 | 部分 | 部分 | ❌ | ✅ | ✅ | ✅ |
| **规范 Lint** | ❌ | ❌ | ❌ | 部分（数据契约） | 部分 | ✅ |
| **AI 产出审批发布闭环** | ❌ | ❌ | ❌ | ❌ | ❌ | ✅ |

**最后两行是空白的。** 现有开源产品的治理要么是「配置管理」，要么是「元数据平台的规则」，**没有把「AI 产出 → 规范校验 → 人工审批 → 发布」做成一条流水线**。

这就是这个项目真正的差异点。

## 五、行业信号

2026 年一个明显的变化：**大家不再叫「BI」或「数据平台」，开始叫「Context Layer」。**

- Wren AI：`governed text-to-SQL through an open context layer`
- DataHub：`The Context Platform for your Data and AI Stack`
- OpenMetadata：`The Open Context Layer for Data and AI`
- Cube：`semantic layer for AI, BI and embedded analytics`

这验证了我们的判断：**语义 + 知识 = 上下文，上下文才是 AI 时代的数据平台核心。**

但同时也意味着：这个方向正在变成红海，窗口期可能只有 1~2 年。

## 六、对单人开发的实际建议

1. **不要 fork 任何一个。** 体量最小的 Wren AI 也有 54 MB、Python + Next.js 全栈，改起来比重写还慢。
2. **抄协议，不抄代码。** 把 Cube 的 `cubes` schema、Wren 的 MDL 拿来对照我们的 `semantic/ecommerce.yaml`，看字段设计差在哪。
3. **考虑复用引擎而非平台。** 如果后期语义层复杂度超过自研能力，可以评估把 Wren Engine 作为语义层引擎，我们只保留「问数编排 + 治理 + 审批 + 前端」——这是差异化的部分。
4. **读 SuperSonic 的解析设计。** 它是中文企业场景 + Java + 双范式，最贴合你们的落地环境。
5. **盯住 license。** DataHub / OpenMetadata / dbt 是 Apache-2.0；Wren / SuperSonic / Cube / Chat2DB 是自定义许可，商用前必须核实。

> 功能上打不过，但贴合你们的口径和流程，这就是一个人能赢的地方。

# 附录：Cube 详解

> 仓库：[cube-js/cube](https://github.com/cube-js/cube) · 21.0k stars · 最新 v1.8.8（2026-10-16）

## A1. 一句话

**开源语义层（semantic layer / headless BI）**：把「指标怎么算」从 SQL 里抽出来，统一用 API 暴露，让 BI、嵌入式分析、AI agent 拿到同一套口径。

## A2. 基本档案

| 项 | 值 |
|---|---|
| 语言 | Rust（Cube Store）+ TypeScript / Node（核心服务） |
| 体量 | 510 MB，单查询服务 + 存储两进程 |
| 许可 | 双许可 Apache-2.0 / MIT（按包，LICENSE 明示），GitHub 识别为 Other |
| 定位 | semantic layer for AI, BI and embedded analytics |
| 关键概念 | Cube / Measure / Dimension / Segment / Join / Pre-aggregation |

## A3. 模型长什么样

模型用 JS/TS 的 `cube()` 函数定义（不是纯 YAML，因此可以写逻辑）：

```js
cube(`Orders`, {
  sql_table: `public.orders`,

  joins: {
    Users: { relationship: `belongsTo`, sql: `${CUBE}.user_id = ${Users}.id` }
  },

  measures: {
    count: { type: `count` },
    gmv: {
      sql: `${CUBE}.paid_amount`,
      type: `sum`,
      filters: [{ sql: `${CUBE}.status = 'paid'` }]
    },
    aov: { sql: `${gmv} / ${count}`, type: `number` }
  },

  dimensions: {
    id:        { sql: `${CUBE}.id`, type: `number`, primaryKey: true },
    channel:   { sql: `${CUBE}.channel`, type: `string` },
    createdAt: { sql: `${CUBE}.created_at`, type: `time` }
  },

  segments: {
    paid: { sql: `${CUBE}.status = 'paid'` }
  },

  preAggregations: {
    dailyByChannel: {
      measures: [gmv],
      dimensions: [channel],
      timeDimension: createdAt,
      granularity: `day`,
      refreshKey: { every: `1 hour` }
    }
  }
})
```

## A4. 查询协议

所有客户端说同一种 JSON：

```json
{
  "measures": ["Orders.gmv"],
  "dimensions": ["Orders.channel"],
  "timeDimensions": [{
    "dimension": "Orders.createdAt",
    "dateRange": "last 30 days",
    "granularity": "day"
  }],
  "segments": ["Orders.paid"],
  "order": { "Orders.gmv": "desc" },
  "limit": 10
}
```

接口：`POST /cubejs-api/v1/load`、`POST /cubejs-api/v1/sql`、`GET /cubejs-api/v1/meta`。

## A5. 架构

```
客户端（BI / 嵌入式 / AI agent）
        │  JSON 查询
        ▼
   Cube API（Node/TS）
        │ ① 校验 + 租户/权限上下文
        │ ② 预聚合路由（命中 → 查 Cube Store）
        │ ③ 未命中 → 动态生成 SQL
        ▼
   Cube Store（Rust）  或  数据源（PG/MySQL/BigQuery/Snowflake/ClickHouse…）
```

## A6. 值得借鉴的 6 个点

| 设计 | Cube 的做法 | 我们的现状 |
|---|---|---|
| **segments** | 预置过滤片段，查询时引用而不是每次写 filters | ❌ 没有 |
| **preAggregations** | 预聚合物化 + 自动路由 + 增量刷新 | ❌ 没有，数据量上来会崩 |
| **timeDimensions** | `dimension + dateRange + granularity` 三合一 | ⚠️ 我们拆成 filter + grain，表达力接近 |
| **queryRewrite** | 查询改写实现行级权限（多租户常用） | ⚠️ 我们是编译期注入 RLS，思路不同 |
| **meta API** | 把模型元数据暴露给前端做字段选择器 | ❌ 我们只有 `/api/meta` 的简化版 |
| **Cube Store** | 独立列存做预聚合，隔离源库压力 | ❌ 无 |

## A7. 优点与坑

**优点**

- 语义层设计成熟，指标定义一次、多端复用
- 预聚合是杀手级能力：把重型查询变成查小表
- 多数据源覆盖广（30+ driver）
- 社区大、文档全、AI agent 叙事跟得紧

**坑**

- **不是 BI 产品**：没有看板、没有可视化编辑器，headless 意味着前端要自己写
- Schema 是 JS/TS，有学习成本，也意味着可以塞任意逻辑（灵活但不适合治理）
- 至少两个进程（API + Cube Store），运维比单进程重
- 预聚合调优有门槛，配错会出现「数据陈旧」或「查询反而变慢」
- 强绑定它的查询协议，换出成本高
- 高级安全 / 多租户能力主要在 Cloud 版

## A8. 我们该不该用

**现在不用。** 我们缺的是数据接入和前端，Cube 帮不上；引入它反而多一层运维。

**什么时候重新考虑**：满足任一条件时，把 Cube 当语义层引擎，我们保留上层（问数编排 + 治理 + 审批 + 看板）：

- 需要接 3 个以上数据源
- 单查询稳定超过 5 秒
- 预聚合成为刚需
- 语义层维护成本超过开发时间的 20%

**判断原则**：**抄协议，不抄引擎。**

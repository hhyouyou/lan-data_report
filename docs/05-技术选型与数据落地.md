# 05 · 技术选型与数据落地

> 原则：**单人能维护 > 技术先进。** 每一个选型都问一句「半年后我还能维护吗」。

---

## 一、选型结论

| 层 | 当前选择 | 理由 | 什么时候换 |
|---|---|---|---|
| 后端 | Python 3.12 + FastAPI | AI 生态最顺、单人效率最高 | 不需要换 |
| 分析库 | **SQLite** → 后期 DuckDB | 零依赖 / 零运维 / 单文件备份 | 单表 > 500 万行或需直读 Excel |
| 元数据库 | 独立 SQLite 文件 | 同上 | 并发写 > 10/s 时换 PG |
| 前端 | 原生 JS + 手写 SVG | 无构建步骤，改完刷新即生效 | v1.0 后局部上 React |
| 语义层 | YAML + Git | 可评审、可 diff、可回滚 | 需多人编辑时加配置页 |
| LLM | OpenAI 兼容接口 | 一行配置换 DeepSeek / Qwen | 需私有化时换本地模型 |
| 部署 | uvicorn + nginx（或 docker-compose） | 单人可维护 | 有团队再上 K8s |

### 为什么先 SQLite 不上 DuckDB / ClickHouse

- 内部工具，数据量预计 **< 1000 万行**，SQLite 完全够
- 零依赖、零运维、一个文件就是全部数据，备份=复制
- 本机 `pip install duckdb` 受限装不上（已验证），SQLite 是标准库
- 迁移成本被适配层隔离：SQL 基本通用，主要是时间函数

**换 DuckDB 的信号**（满足任一）：

- 单表 > 500 万行且典型查询 > 2 秒
- 想直接 `SELECT * FROM 'xxx.xlsx'` 不进库
- 需要和 pandas 高频互转
- 需要的分析函数 SQLite 不支持（窗口函数 SQLite 3.25+ 已支持，基本够）

迁移点只有两处：`server/app/executor.py`（连接与执行）和 `compiler.py` 里的时间函数（`strftime` 语法两者兼容）。

### 为什么前端不上 React

- v1.0 前只有 3 个视图：问数、看板、配置
- 无构建步骤意味着改完刷新就生效，单人迭代最快
- 手写 SVG 图表保证离线可用（内部网络经常访问不了 CDN）
- v1.0 后如果要做拖拽式看板，再局部引入 React，接口不变

## 二、数据落地：三层

```
raw（原始层）      staging（清洗层）      mart（可用层）
Excel / CSV    →   类型统一、字段映射  →  标准事实表 + 维表
业务库导出          去重、补全、打标         语义模型只依赖这一层
API / 共享目录
```

### 三条规则

1. **raw 只追加不改**：保留原始证据，出问题能回溯
2. **staging 做规范化**：字段名、类型、枚举值统一
3. **mart 才给语义层用**：表必须带主键、时间字段

### mart 表的硬性约定

| 约定 | 说明 |
|---|---|
| 主键 | 每张事实表必须有业务主键，用于去重 |
| 时间字段 | 至少一个 ISO 格式时间列（`YYYY-MM-DD HH:MM:SS`） |
| 分区字段 | 大表加 `dt`（`YYYY-MM-DD`），便于增量同步和清理 |
| 金额 | 用 REAL/DOUBLE 存，展示时格式化；涉及对账时用整数分 |
| 枚举 | 统一取值（如渠道固定 5 个值），写进语义模型的 `dictionary` |

## 三、Excel 导入（占比最高）

> ✅ **已实现**：`server/app/datasets.py`
> API：`POST /api/tables/import`、`POST /api/tables/{name}/draft-model`、`POST /api/semantic/drafts`

业务数据 80% 在 Excel 里。导入流程：

```
data/inbox/xxx.xlsx
  → 读表头 + 推断类型
  → 字段映射（中文表头 → 英文字段名）
  → 生成/校验建表语句
  → 写入 mart 表
  → 输出导入报告（行数、失败行、类型警告）
```

### 已实现的自动化能力

| 步骤 | 做法 |
|---|---|
| 列名清洗 | 中文表头 → 英文标识（订单金额→`amt_order`、是否新客→`is_new_user`），原表头保留在元数据里 |
| 类型推断 | 自动识别 `time` / `number` / `boolean` / `string` |
| 日期识别 | 字符串列中 >90% 可解析为日期的，转 datetime |
| 布尔识别 | 列值 ⊆ {是,否,true,false,y,n,1,0} 的，转 boolean |
| 语义草稿 | 数值列→指标（按金额/数量/比率给不同 agg 与 format），低基数列→维度+值字典 |
| 规范校验 | 草稿生成后自动跑 `standards.lint("semantic")` |

### 必须处理的坑

| 坑 | 处理 |
|---|---|
| 中文表头 | 启发式映射 + 保留原表头；接 LLM 后可升级为模型生成 |
| 日期格式混乱 | 多格式尝试解析，失败的写 `_import_errors` 表 |
| 金额带 ¥ / 千分位 | 清洗后再转数值 |
| 合并单元格 / 多行表头 | 人工指定 `header_row` |
| 重复导入 | 按主键 upsert，不要 append |
| Excel 打开着 | 提示用户关闭（Windows 文件锁） |

> 建议做成 CLI 脚本而不是 UI：`python tools/import_excel.py --file xx.xlsx --table fact_order`
> 单人阶段，脚本 + 配置文件的维护成本远低于导入向导。

## 四、业务库接入

只读账号 + 定时同步到本地仓库，**不做实时**。

```
MySQL/PG（只读账号）
   → 增量拉取（WHERE updated_at > last_sync）
   → 落到本地 mart 表
   → 记录同步水位
```

- 小表（维表）全量同步
- 大表（事实表）按时间增量
- 同步脚本 + Windows 计划任务 / cron 即可，**不要上 Airflow**

### 为什么同步到本地而不是直连查询

| 方式 | 优点 | 缺点 |
|---|---|---|
| 直连业务库 | 数据实时 | 影响生产库；跨库 join 困难；网络抖动 |
| 同步到本地 | 稳定、不影响业务库、可自由 join | 有延迟 |

内部报表场景延迟 1 小时通常可接受；如果要求实时再单独讨论。

## 五、采集的边界（重要）

**采集是最容易吃掉全部时间的部分，必须划死边界。**

| 做 | 不做 |
|---|---|
| 定时调用已有 API | 网页爬虫 / 验证码 / 反爬对抗 |
| 扫描共享目录里的导出文件 | 需要登录态的自动化操作 |
| 对接开放平台接口 | 需要申请资质的数据源 |

如果数据源不稳定，先做「人肉导出 + 定时扫描目录」，成本最低、最快见效。

## 六、部署（单人版）

### 最简方式（推荐先用这个）

```
内网一台机器
├── nginx（可选，反代 + 静态文件）
├── uvicorn server.app.main:app --host 0.0.0.0 --port 8765
└── Windows 计划任务 / cron：定时跑同步脚本
```

### docker-compose（需要多环境时）

```yaml
services:
  api:
    build: .
    command: uvicorn server.app.main:app --host 0.0.0.0 --port 8765
    volumes: ["./data:/app/data", "./semantic:/app/semantic"]
    ports: ["8765:8000"]
```

### 备份

真正需要备份的只有这几样：

```
data/warehouse.sqlite     # 真实：江苏统计年鉴
data/demo.sqlite          # 演示：合成电商
data/metadata.sqlite      # 元数据：查询 / 看板 / 审批
semantic/
```

每天打包到共享盘即可。**恢复 = 拷贝这几个文件回来。**

## 七、配置项一览

| 环境变量 | 作用 | 默认 |
|---|---|---|
| `LDR_WAREHOUSE` | 真实分析库路径 | `data/warehouse.sqlite` |
| `LDR_DEMO` | 演示库路径 | `data/demo.sqlite` |
| `LDR_META` | 元数据库路径 | `data/metadata.sqlite` |
| `LDR_MODEL` | 语义模型名 | `ecommerce` |
| `LDR_CACHE_TTL` | 查询缓存秒数 | `300` |
| `LLM_BASE_URL` | OpenAI 兼容接口地址 | 空（走规则引擎） |
| `LLM_API_KEY` | API Key | 空 |
| `LLM_MODEL` | 模型名 | `deepseek-chat` |

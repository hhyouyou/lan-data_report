# 08 · 数据开发 Agent 方案

> 一句话：**不是一个会聊天的机器人，是一条有产物、有校验、有人工卡点的流水线。**

> **状态：⏸ 暂缓（2026-10-20）**。MVP1 已实现过一次后被主动回退——目标过大，先聚焦数据分析与看板。
> 本文保留作为后续参考，不体现在当前产品中。

---

## 一、定位与边界

| 是 | 不是 |
|---|---|
| 数据开发 / 代码开发领域的专用 Agent | 通用 Agent |
| 阶段化、有产物、可审批 | 自由对话、自由发挥 |
| 人在 3 个节点确认 | 全自主交付 |
| 复用 harness 的 runtime | 自研 Agent 框架 |

**边界**：只做数据开发（接入 / 清洗 / 建模）和配套代码，不做业务决策。

---

## 二、核心判断：Agent 上限由「验证信号」决定

Coding Agent 强，是因为代码有编译器 + 测试作为天然反馈。

数据开发没有。模型"能跑"不等于"算对"。所以如果只给 Agent「能执行查询」这一个信号，它会稳定产出**能跑但算错**的模型，而且自认为完成。

**所以这个方案的重点不是 Agent，是验证层。**

| 验证信号 | 实现 |
|---|---|
| 结构校验 | `semantic.validate()` |
| 规范 Lint | `standards.lint()` |
| 数据质量 | 行数、空值率、维度基数、列存在性 |
| 口径回归 | 与基线结果比对（阈值内） |
| 交叉验证 | 两条独立路径算同一指标 |
| 人工卡点 | `workflow` 审批 |

---

## 三、流水线：阶段 × 产物 × 校验

```
① 理解 ──▶ ② 规划 ──▶ ③ 生成 ──▶ ④ 验证 ──▶ ⑤ 文档 ──▶ ⑥ 交付
   │          │          │          │          │          │
analysis    plan       model     verification  document   submit
```

| 阶段 | 输入 | 产物 | 校验 | 人工卡点 |
|---|---|---|---|---|
| ① 理解 | 自然语言需求 + 表清单 | `analysis`：表、指标诉求、维度诉求、粒度、假设、歧义 | 表存在、需求可解析 | ✅ 需求确认 |
| ② 规划 | analysis | `plan`：指标→列映射、维度→列映射、聚合方式 | 列存在、类型匹配 | — |
| ③ 生成 | plan | `model`：语义层 YAML | `validate()` | — |
| ④ 验证 | model + 数据 | `verification`：检查项列表 | 全部检查 | ✅ 验收 |
| ⑤ 文档 | 全部产物 | `document`：模型说明 Markdown | 文档完整度 | — |
| ⑥ 交付 | model | 保存 / 激活 / 提审批 | `lint()` | ✅ 发布 |

**硬规则**

1. **状态机由代码控制**，不让 Agent 自己判断"下一步该干嘛"
2. **每个阶段只认上一阶段的产物**，不认聊天记录 → 长任务不漂移
3. **没有通过验证 = 不算完成**，状态置为 `needs_fix`
4. **产物可 diff、可回滚、可审批**，复用现有 workflow

## 四、工具层（Agent 能做的事）

| 类别 | 工具 | 现状 |
|---|---|---|
| 数据 | `list_tables` / `table_detail` / `import_file` | ✅ |
| 查询 | `run_spec` / 原始 SQL（只读） | ✅ |
| 建模 | `draft_model` / `apply_patch` / `semantic_lint` | ✅ |
| 校验 | `data_quality` / `baseline_compare` | 🚧 MVP1 |
| 文档 | `render_document`（模板填充） | 🚧 MVP1 |
| 交付 | `save_draft` / `activate` / `submit_approval` | ✅ |

**工具白名单**：只读 + 写草稿，不允许改写线上模型；所有写操作走审批。

## 五、产物规范

所有产物是**结构化 JSON + 渲染后的 Markdown**，不是自由文本。

```jsonc
// analysis
{
  "table": "t_sales",
  "goal": "按渠道和地区看 GMV 和客单价",
  "metrics_requested": [{"raw": "GMV", "column": "amt_order", "agg": "sum"}],
  "dimensions_requested": ["channel", "region"],
  "grain": "day",
  "assumptions": ["未指定时间范围，默认全量数据"],
  "ambiguities": ["「客单价」按 GMV/订单量计算"]
}
```

## 六、框架选择

**用 coding agent 的 runtime，自研数据领域的工具和验证。**

| 复用 | 自研 |
|---|---|
| 工具调用、文件系统、沙箱执行 | 领域工具（导数据 / 跑 SQL / Lint / 出文档） |
| 长上下文、检查点 | 编排状态机 |
| 子 Agent 并行（调研 / 审查） | 验证器 + 评测集 |

> 提醒：coding harness 天生优化「代码能过测试」。必须把目标函数换成「模型能过数据验证」，
> 否则它会产出漂亮、能跑、但错误的东西。

---

## 七、评测集（没有它就不算工程）

| 类型 | 例子 | 判定 |
|---|---|---|
| 正常需求 | 「按渠道看 GMV」 | 模型结构正确 + 验证通过 |
| 模糊需求 | 「看看销售情况」 | 应反问 / 给出假设 |
| 缺数据 | 「分析用户留存」但表里没有 | 应明确说明无法建模 |
| 脏数据 | 关键列空值率 80% | 验证应报 fail |
| 冲突需求 | 「按日期和月份拆分」 | 应提示粒度冲突 |

评测指标：**建模成功率、验证通过率、假设命中率、人工返工率**。

## 八、MVP 路线

| 版本 | 范围 | 验收 |
|---|---|---|
| **MVP1** | 建模段：理解 → 规划 → 生成 → 验证 → 文档 | 5 个真实需求，4 个产出可用模型 |
| MVP2 | 加需求澄清 + PRD 模板 | 澄清轮次 ≤ 2 |
| MVP3 | 加数据接入 / 清洗自动化 | 能从 Excel 到模型全自动 |
| MVP4 | 全流水线 + 审批 + 回归评测 | 端到端 30 分钟内交付 |

**为什么从建模段开始**：只有这一段有强验证信号（能跑、能对账、能 Lint）。
先让 Agent 证明自己靠谱，再往前扩。

---

## 九、失败模式清单

| 失败模式 | 表现 | 对策 |
|---|---|---|
| 伪自主 | 报告完成但数字错 | 强制验证，不通过不算完成 |
| 文档通胀 | 生成 30 页没人看 | 模板 + 字数上限 |
| 上下文爆炸 | 全库表结构塞 prompt | 元数据检索 + 分层摘要 |
| 错误累积 | 需求偏 10% → 模型错 100% | 每阶段人工卡点 |
| 沉默退化 | 换模型后能力下降没人知 | 评测集 CI |
| 权限越界 | Agent 直接改线上模型 | 只写草稿 + 审批发布 |

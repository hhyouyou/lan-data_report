# 06 · 规范与审批：把治理做成可执行的

> 核心判断：**规范如果只写在文档里，AI 不会读，人也会忘。规范必须是可执行的。**

所以这里不写「制度」，写三件东西：

```
规范即代码（standards/*.yaml）
   ├── context_pack()  →  注入 AI 的 prompt（AI 读得到）
   ├── lint()          →  机器自动校验（机器拦得住）
   └── workflow        →  提交 → 审批 → 发布（人把最后一道关）
```

同一份 YAML 派生三样产物，永远不会出现「文档说一套、代码做一套」。

---

## 一、建模规范

文件：[standards/modeling.yaml](../standards/modeling.yaml)

| 模块 | 内容 |
|---|---|
| **数仓分层** | ODS / DIM / DWD / DWS / ADS，每层的职责与表前缀 |
| **命名规范** | 表名 `{层}_{域}_{主题}_{后缀}`、字段 snake_case、指标/维度命名、后缀词典 |
| **数据域** | 交易 / 用户 / 商品 / 营销 / 售后，每域的 owner |
| **标准术语** | GMV、订单量、客单价等 canonical 名与同义词 |
| **必填元数据** | 表：owner/描述/层/域/更新频率/粒度；指标：title/format |
| **执行级别** | 每条规则可配 error（阻断）/ warn（提示）/ off |

### 为什么要有「执行级别」

存量系统一上来不可能全部合规。如果第一天就把命名设成 error，AI 生成的东西全被拦住，平台没法用。

推荐路径：

```
接入期：table_naming=warn, field_naming=warn  → 先跑起来，积累问题清单
治理期：存量改完 → 调成 error                → 新的必须合规
```

## 二、报表规范

文件：[standards/reporting.yaml](../standards/reporting.yaml)

| 模块 | 内容 |
|---|---|
| **视觉规范** | 固定调色板、字号、间距、12 栅格 |
| **图表选择矩阵** | 场景 → 图表类型（时间趋势用折线、类别对比用柱状、占比用饼图且 ≤6 类…） |
| **布局规范** | 顶部指标卡、筛选器统一、单卡 ≤12 栅格、卡片 ≤12 张 |
| **命名规范** | 看板 `{业务域}{周期}{主题}分析`、卡片 `{指标} · {维度}（{时间范围}）` |
| **禁忌清单** | 3D 图、饼图超 6 类、超 5 系列色、柱状图截断 Y 轴、默认卡片名… |

这张表是为了解决你说的「每次生成的报表风格各异」：**图表类型不再由 AI 自由发挥，而是查表决定**。

## 三、自动 Lint

实现：`server/app/standards.py`

### 建模规则

| 规则 | 级别（默认） | 说明 |
|---|---|---|
| `metric_naming` | error | 指标名必须匹配 `^[a-z][a-z0-9_]*$` |
| `dimension_naming` | error | 同上 |
| `required_metadata` | warn | 缺 title / format |
| `time_dimension` | error | 必须至少有一个时间维度 |
| `table_naming` | warn | 表名不符合分层命名 |
| `field_naming` | warn | 字段不符合 snake_case |
| `synonym_uniqueness` | warn | 同一同义词指向两个实体 |
| `keyword_consistency` | warn | 术语与标准名不一致 |

### 报表规则

| 规则 | 级别 | 说明 |
|---|---|---|
| `title_required` | error | 看板标题不能为空 |
| `chart_type` | error | 图表类型必须在白名单 |
| `layout_bounds` | error | 布局越界 / 卡片 id 重复 |
| `layout_overlap` | warn | 卡片互相重叠 |
| `card_title` | warn | 标题为空或使用「图表1」这类默认名 |
| `max_cards` | warn | 卡片数超过 12 |

### 接口

```http
POST /api/standards/lint
{ "kind": "semantic" | "dashboard", "doc": { ... } }

→ { "kind": "dashboard", "passed": false,
    "errors":   [{"rule":"chart_type","severity":"error","message":"...","target":"c1"}],
    "warnings": [...] }
```

## 四、审批发布工作流

实现：`server/app/workflow.py`

```
                     ┌──────────────────────────────┐
                     │                              │
  draft ──submit──▶ submitted ──approve──▶ approved ──publish──▶ published
    ▲                   │                                          │
    │                   └──reject──▶ rejected                     │
    │                                    │                       │
    └────────────── submit（重新提交）◀───┘                       │
                                                                  │
    ◀────────────── edit（内容变更自动退回 draft）────────────────┘
```

### 硬规则

1. **提交前自动跑 lint**，有 error 直接拒绝，并返回完整问题列表。
2. **只有 `published` 才能生成分享链接**，草稿/审批中/已通过都不行。
3. **内容变更自动退回 draft**：Pin 新卡片、PATCH 看板都会触发 `mark_dirty`，已发布的看板需要重新审批。
4. **每次状态变化都写入时间线**，谁在什么时候提交/审批/发布，可审计。
5. **发布 = 把快照写入线上版本**，审批期间编辑不影响线上。

### 接口

```http
POST /api/dashboards/{id}/submit          # 提交（自动 lint）
POST /api/artifacts/{aid}/approve         # 通过
POST /api/artifacts/{aid}/reject          # 驳回（带原因）
POST /api/artifacts/{aid}/publish         # 发布
GET  /api/artifacts?status=submitted      # 审批中心
GET  /api/dashboards/{id}/workflow        # 当前审批状态 + 时间线
```

### 实测

```
1. 创建看板            状态=draft
2. Pin 一张卡片         卡片数=1
3. 分享                → 400（未发布）
4. 提交审批            状态=submitted，lint 通过
5. 审批通过            状态=approved
6. 分享                → 400（已通过但未发布）
7. 发布               状态=published
8. 分享                → /?share=42b0... ✅
```

## 五、「Skill」到底落地成什么

你说的「形成固定的 skill」，拆开是四样东西：

| Skill 的组成 | 本项目里的载体 | 状态 |
|---|---|---|
| **规范正文** | `standards/modeling.yaml`、`standards/reporting.yaml` | ✅ |
| **给 AI 的注入形态** | `context_pack()` → `GET /api/standards/context` | ✅ |
| **验收标准** | `lint()` → 提交时强制执行 | ✅ |
| **脚手架模板** | `templates/` + `POST /api/templates/{id}/render` | ✅ |

前三样是「AI 知道该怎么做 + 做错会被拦」，第四样是「AI 不用从零想」。

### 模板库（templates/）

```
templates/
  tables/  dwd_fact_table.yaml      DWD 明细事实表
           dim_table.yaml           DIM 维度表
           dws_summary_table.yaml   DWS 汇总表
  cards/   trend_line.yaml          趋势折线
           kpi_card.yaml            核心指标卡
           category_bar.yaml        分类对比柱状
  boards/  business_review.yaml     经营分析看板（6 张卡）
```

模板格式：

```yaml
id: dwd_fact_table
kind: table                 # table | card | dashboard
variables:                  # 参数声明，含默认值与可选项
  - { name: domain, required: true, options: [trade, user, product, marketing, aftersale] }
  - { name: suffix, required: false, default: _di }
body: |                     # 结构模板，{var} 会被替换
  table: "dwd_{domain}_{subject}{suffix}"
  layer: dwd
```

使用方式：

```http
GET  /api/templates                       # 列出所有模板
POST /api/templates/dwd_fact_table/render # 渲染，返回 doc + lint 结果
POST /api/templates/business_review/create-dashboard
     { "params": { "title": "交易域2026年9月经营分析" } }
```

实测渲染 `dwd_fact_table(domain=trade, subject=order_detail)`：

```yaml
table: dwd_trade_order_detail_di
layer: dwd
owner: 交易数据组
lint: passed（0 错误 0 提示）
```

实测从看板模板一键生成：

```
6 张卡片全部落库并取到数
  c_kpi_gmv    rows=1  kpi   9,579,373.33
  c_kpi_order  rows=1  kpi   4,612
  c_trend      rows=29 line
  c_category   rows=6  bar
  c_channel    rows=5  bar
```

**这解决了「每次风格各异」的根因**：AI 不再从零生成一张表或一个看板，而是选模板 + 填参数，结构天然一致。

## 六、怎么扩展到其他产出

这套机制是通用的，`workflow` 的 `kind` 字段已经预留：

| 产出类型 | 接入方式 | 备注 |
|---|---|---|
| 看板 | 已接入 | dashboard |
| 语义模型 | `kind=semantic`，lint 已实现 | 平台内审批 or Git MR，二选一 |
| 数据集 / 清洗管道 | 加 lint 规则 + 沙箱预览 | 需先做执行沙箱 |
| 定时报表 / 订阅 | 复用同一状态机 | Phase C |

> 建议：语义模型短期走 **Git MR**（有 diff、有评审、有历史），平台内只审批看板这类「在平台里长出来的产出」。两套流程并存比强行统一更省事。

## 七、语义模型走 Git MR（已定）

**决策：语义模型和表结构走 Git MR，平台内只审批看板这类「在平台里长出来的产出」。**

| 产出 | 审批方式 | 理由 |
|---|---|---|
| 看板 / 卡片 | 平台内审批 | 频繁修改、业务方参与、需要在界面上看效果 |
| 语义模型 `semantic/*.yaml` | **Git MR** | 影响面大、需要 diff、有历史、要有回滚 |
| 表结构规格 | **Git MR** | 同上 |

平台侧通过 `GET /api/policies` 暴露这个约定；对 `kind=semantic/table` 调用 submit 会被直接拒绝：

```
semantic 类产出按约定走 Git MR（有 diff、有评审、有历史），不在平台内提交审批
```

### 门禁脚本

[tools/semantic_gate.py](../tools/semantic_gate.py) 在 pre-commit / CI 里跑，保证合并的语义模型合规：

```bash
python tools/semantic_gate.py            # 检查 semantic/ 下所有模型
python tools/semantic_gate.py --strict   # warn 也算失败（治理期）
```

输出示例：

```
▸ semantic\ecommerce.yaml  (ecommerce)
  ⚠ [table_naming] 表名 fact_order 不符合规范 ^(ods|dim|dwd|dws|ads)_[a-z]...
  ✓ 通过
汇总: 0 个错误, 1 个提示
```

接入 Git：

```bash
# .git/hooks/pre-commit（或 husky / lefthook）
#!/bin/sh
python tools/semantic_gate.py --strict || exit 1
```

## 八、审批权限

`LDR_APPROVERS` 环境变量配置审批人白名单（逗号分隔）：

```bash
LDR_APPROVERS=zhangsan,lisi
```

- 未配置：不限制（本地开发）
- 已配置：非白名单用户调用 approve/reject/publish 返回 **403**
- 提交（submit）不限制，任何人都能提交

```http
POST /api/artifacts/{aid}/approve
X-User: zhangsan          → 200
X-User: bob               → 403 用户 bob 没有审批权限
```

> 单人开发阶段可以先不配，自己批。但建议在正式推广前配一个业务方，
> 因为「谁批的」是口径被信任的凭证。

## 九、落地建议

1. **规范文件放 Git，跟代码一起评审**。改命名规则就是一次代码变更。
2. **从 warn 起步**，先跑两周收集问题，再逐条收紧成 error。
3. **每遇到一个新问题，就加一条 lint 规则**——规范是长出来的，不是一次写完的。
4. **审批人不要是自己**。单人开发阶段可以先自己批，但建议拉一个业务方做形式上的把关，这是「口径被信任」的开始。
5. **不要做审批流引擎**。现在的状态机 30 行就够，别上 BPM。
